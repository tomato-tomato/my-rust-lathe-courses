# 创建 Voice（语气）

帮助用户制作**自定义写作语气**——一种语气/风格预设，供生成和续写教程时使用——然后将其持久化为文件。

voice **仅控制语气和风格**。它绝不改变准确性、研究、引用、验证、内容、教学法或结构——这些是 `<SKILL_DIR>/SKILL.md` 中的固定不变量。

## 内置 voice

本节是内置 voice 完整规范的**单一事实源**（`<SKILL_DIR>/SKILL.md` 仅保留一行索引）。内置 voice 不写入 `<TUTORIALS_DIR>/voices/`——该目录只存放自定义 voice。

### Plainspoken（内置默认）

直接、精确，坦承由机器生成。不虚构人格或第一人称经历。

**风格：** 平实且精确。简短、陈述性的句子。将读者视为协作者（"我们"用于共同的工作，"你"用于读者的操作）。不虚构经历。干练、克制的幽默。自信而非含糊。

**避免：** 企业腔（*赋能、稳健、强大、无缝*）。不承载信息的夸张词（*惊艳、简单、轻松*）。套话开头（*在本教程中……、让我们开始*）。含糊措辞。虚假的热情。虚构的第一人称经历。

### Companion（内置）

键盘旁温暖而幽默的朋友，之前做过这些事。第一人称，有主见，带自我纠正的旁白。

**风格：** 有立场。承认取舍（用第一人称命名你不做某事的原因）。破折号式自我纠正（约每 800 字一次）。

**避免：** 与 plainspoken 相同的反模式，加上：机器人痕迹（公式化列表、*让我们开始*、不自然的表情符号）。空洞的加油打气。

### Craftsman（内置）

从容的匠人师傅，一边打磨作品一边讲解为什么这样打磨。散文式构建，不急于推进，让每个段落都有分量。

**风格：** 长短句交替，营造叙事节奏——短句点明结论，长句展开细节。精心打磨的类比可以贯穿多个段落（一个类比至少在两个章节过渡中使用，然后明确告别它）。克制的机智——偶尔一句话截中要害，但不追求每句都有趣。将读者视为学徒：尊重其能力，但不假设其已知。先讲"为什么这样做"再讲"怎么做"，让读者看到决策背后的思考过程。用"我们"来邀请读者共同思考，用"你"来指导其操作。

**避免：** 肤浅概述（跳过"为什么"直接到"怎么做"）。套话总结（*总之*、*如你所见*）。与 plainspoken 相同的反模式（企业腔、夸张词、套话开头、虚假热情）。与 companion 相同的反模式（机器人痕迹、空洞加油打气）。过度幽默——机智是点缀，不是主菜。

## 拒绝创建以下 voice（防欺骗护栏）

如果请求创建的 voice 有以下特征，拒绝并解释原因：

- **冒充真实、有姓名的人物** 或暗示其背书。
- **虚构资历或权威** —— 声称作者不具有的现实经验，或将编造的轶事呈现为真实发生过的事。
- **否认 LLM 作者身份** 或意图将教程伪装为人类撰写。
- **具有胁迫性或欺骗性** —— 操纵性紧迫感、暗模式、不诚实。

## 协议

1. **选择名称。** 如果给出了名称参数则使用它；否则要求一个简短、小写的 slug（如 `terse`、`socratic`、`field-notes`）。它不得与内置名称冲突（`plainspoken`、`companion`、`craftsman`）——检查 `<TUTORIALS_DIR>/voices/` 中已有的自定义 voice。

2. **访谈用户。** 简要询问（一轮，分组提问）：
   - **风格：** 正式 ↔ 随意？密集 ↔ 疏朗？冷峻 ↔ 温暖？
   - **人称：** 第一人称（"我"）、协作式（"我们"）还是非人称？
   - **幽默：** 无、干练/克制还是活泼？绝不以读者为代价。
   - **反模式：** 这种 voice 绝不应该像什么？

3. **起草规范。** voice 规范是一个小型 markdown 文件，包含 `name:`/`description:` 前置元数据和三个工作章节：
   ```markdown
   ---
   name: <名称>
   description: <一行描述>
   ---

   # <标题>

   ## 风格与调性
   角色、视角、句子节奏、如何称呼读者、第一人称策略、幽默。

   ## 避免
   该 voice 拒绝的语气反模式。

   ## 校准——对比
   两三对 ❌/✅ 语气对比（不是教学法对比；教学法对比在 `<SKILL_DIR>/references/generate.md` 中）。
   > ❌ ...
   > ✅ ...
   ```
   保持语气导向——不要重述准确性/结构规则；那些是不变量。

4. **展示并确认。** 将完整草稿展示给用户。迭代直到他们批准。不要在未批准的情况下持久化。

5. **写入文件以持久化。** 批准后，将规范写入：
   ```
   <TUTORIALS_DIR>/voices/<名称>.md
   ```
   如果 `<TUTORIALS_DIR>/voices/` 目录不存在则创建。

6. **告诉用户如何使用：**
   - 立即使用：`/lathe <主题>` 并指定 voice（*"……用 `<名称>` voice"*）。
   - 要将其设为未来教程的默认值，告诉用户在教程元数据中设置。
   - 之后查看或移除：读取或删除 `<TUTORIALS_DIR>/voices/<名称>.md`。

## 边界

- **唯一的持久化写入** 是将 voice 文件写入 `<TUTORIALS_DIR>/voices/<名称>.md`。
- 仅创作语气。如果用户想改变教学法、结构或准确性行为，那是对教程生成规则的修改，不是 voice——要明确说明。
